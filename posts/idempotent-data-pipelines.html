Idempotent Data Pipelines

A scheduler hiccups, a task silently reruns, or someone kicks off a backfill on data that was already processed. Suddenly a table that should show one number shows double. Here is how I think about the fix, with a Netflix style example to make it concrete, and a small local project I built to prove it to myself.

If you have worked in data engineering for more than a week, you have probably seen this happen. That is the exact problem idempotence solves.

What Idempotence Actually Means

An operation is idempotent if running it once or running it five times leaves you with the same result. In data engineering terms, if my pipeline runs multiple times with the same input, whether because of a scheduler misconfiguration, a zombie task that is technically dead but still writing in the background, or an intentional backfill, I should still get a consistent, correct output.

Why this matters in practice:

  • Rerunning a load should not duplicate data
  • A failed job should be safely retryable, not manually cleaned up
  • Backfills should not introduce side effects you did not intend
  • Unique constraints should never get compromised by a rerun

The Two Patterns That Get You There

Delete and write. Before loading new data for a given slice, usually a date, you delete whatever already exists for that slice, then insert the freshly computed data. Run it once or run it ten times, you land in the same place. This works well when the upstream source itself can change retroactively, since you are always doing a full, clean replace rather than reconciling old and new rows.

Merge, also called upsert. Instead of wiping and reloading, you match incoming rows against a unique key already in the target table. If the key exists, you skip it. If it does not, you insert it. This is the better choice when the source is trustworthy and effectively immutable once written, like a staging table fed by completed transactions.

One detail that trips people up: the merge pattern does not need to wait for tomorrow to fill in a failed load. If a job dies halfway through, you can rerun the exact same job right away. The rows that already landed get skipped because their key already exists, and only the missing rows get inserted. Same run, same date, no waiting.

The other detail worth remembering is to always parameterize by something explicit like a date, never by CURRENT_DATE or today. If your job's identity depends on when it happens to run rather than what it was asked to process, you have already broken idempotence before you even get to delete or merge logic.

Making It Concrete: A Netflix Style Example

To make this tangible, I walked through how a company like Netflix might apply this to viewing events. Worth being upfront that this is an illustrative scenario, not a claim about Netflix's actual internal stack.

Picture a daily job that computes total watch hours per title. Every play, pause, or skip fires a raw event that lands in a staging table. From there, a daily aggregate table gets built for dashboards.

Two idempotence problems show up immediately. If the scheduler double triggers the job for a given day, a title's watch hours should not double count. If a backfill reprocesses two weeks of history because of a bug fix, it should not stack a second copy of those numbers on top of the first.

The fix maps directly onto the two patterns above, applied by layer:

  • Staging layer (raw, near immutable events): merge and upsert on a unique event id. Since a completed playback event will not retroactively change, you only ever insert what is missing.
  • Mart layer (the daily aggregate table used by dashboards): delete and write, scoped tightly to the date being reprocessed. This is an aggregate, so a clean replace makes more sense than trying to reconcile individual rows.

If this were built in dbt on top of a warehouse like Snowflake, this maps almost exactly onto dbt's incremental materialization. Staging models typically use the merge strategy keyed on a unique id, and mart models typically use delete+insert keyed on the date being reprocessed.

Proving It To Myself Locally

Reading about idempotence is one thing. Watching a table actually double, then watching that stop happening, is another.

I built a small project using nothing but Python's standard library and SQLite, so it runs anywhere with zero setup. It has three pieces: a script that generates a day of fake viewing events into a CSV, a naive pipeline that blindly inserts into a staging table and an aggregate table, and a fixed pipeline that applies merge and upsert to staging, and delete and write to the aggregate table.

Running the naive version twice for the same date is all it takes to see the problem. Raw event counts double. The aggregate table ends up with two rows per title, one of them exactly twice the correct value.

Running the fixed version three, four, five times in a row for the same date changes nothing. Row counts hold steady. Totals hold steady. That is idempotence, not as a definition, but as something you can actually watch happen on your own machine.

The Takeaway

Idempotence is not a fancy concept. It is really just answering one question honestly: if this job runs twice by accident, what happens? If the answer is anything other than nothing changes, that is the bug idempotence is there to fix, and delete and write or merge and upsert are almost always the two tools that get you there.
